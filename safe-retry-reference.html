Safe Retry Reference
for n8n

A deliberately tiny workflow for the awkward moment after automation failure: do I know enough to retry without doing the side effect twice?

What the example proves

  • Three synthetic events enter the workflow.
  • One approved event becomes a draft-only simulated write.
  • One event stops at a human approval boundary.
  • A duplicate event_id is held rather than processed twice.
  • A final receipt verifies that every input was accounted for and no outward action occurred.

Executed locally in n8n 2.17.7. The runtime receipt passed every check.

The important limit

The example uses an in-memory Set() to make the duplicate visible and easy to inspect. That only protects one execution. It is not durable idempotency.

Production retry safety may require a persistent idempotency ledger, a provider-supported idempotency key, a unique database constraint, or read/reconcile logic around the external system. If a request times out after a write, the outcome can be unknown. “I got an error” is not the same fact as “nothing happened.”

Four-node shape

  1. Manual Trigger
  2. Synthetic Side-Effect Events creates one approved, one unapproved, and one duplicate event.
  3. Approval + Idempotency Gate refuses duplicates and unapproved work.
  4. Verification Receipt checks counts and confirms zero outward actions.

This reference has no credentials, customer data, cloud models, HTTP requests, database writes, or production integrations.

Use it as a test fixture, not a talisman

Import the JSON, inspect every node, run it, then replace the synthetic draft with your own rehearsal logic before connecting a real side effect. Add durable dedupe and reconciliation appropriate to the system you are actually touching.
